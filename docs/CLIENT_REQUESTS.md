## 1. 🔴 คลิปที่มีหลายท่าปนกัน (สำคัญที่สุด)

**ปัญหา**: ทุกคลิปในชุดปัจจุบันมีท่าเดียวล้วน ๆ (ถ่ายแบบซ้อมทีละท่า) และ
**ไม่มีคลิปไหนเลยที่มีทั้งสไลซ์และวอลเลย์อยู่ด้วยกัน (0 คลิป)**

**ผลที่ตามมา**: "คลิปไหน" ทำนาย "ท่าอะไร" ได้ 100% → อะไรก็ตามที่ติดมากับคลิป
(ระยะกล้อง มุมกล้อง แสง) กลายเป็นตัวทำนายที่สมบูรณ์แบบโดยไม่ต้องดูท่าทางเลย
เราจึง **พิสูจน์ไม่ได้ว่าโมเดลแยกท่าได้จริง หรือแค่จำว่าเป็นคลิปไหน**

**ขอ**: คลิปตีโต้จริงที่มีหลายท่าสลับกันในคลิปเดียว โดยเฉพาะ **สไลซ์กับวอลเลย์**

รายละเอียด: [STROKE_CLASSIFICATION.md](STROKE_CLASSIFICATION.md)

|---|---|---|
| **FH** | **2** | 20 จาก 21 ตัวอย่างเป็นของผู้เล่นคนเดียว |
| **SL** | **2** | |

| VL | 3 | |

จึงแกว่งตามความบังเอิญ

**ขอ**: ผู้เล่นเพิ่ม โดยเฉพาะ **โฟร์แฮนด์และสไลซ์** อย่างน้อยท่าละ 5-6 คน

> ✅ **ไม่ต้องรอเรา** — เราทำสคริปต์ไว้แล้ว วางไฟล์ลง `dataset/sessions/<ชุด>/`
> แล้วรัน `python scripts/retrain_with_new_data.py` คำสั่งเดียวจบ
> มันจะตรวจไฟล์ label ให้ก่อน เทรนใหม่ แล้ว **เขียนทับเฉพาะเมื่อวัดแล้วดีขึ้นจริง**
> (ถ้าแย่ลงจะไม่เขียนทับ — ข้อมูลเพิ่มไม่ได้แปลว่าดีขึ้นเสมอไป)

## 4. 🔴 ตำแหน่งลูกที่ตก — ต้องเคาะร่วมกัน

**ปัญหา**: ระบบเห็นลูกที่ลอยจริงแค่ **4.4% – 22% ของเฟรม** (ที่เหลือคือค่าที่
Kalman filter เดาต่อเอง ไม่ใช่การวัดจริง) และ **ยังไม่มี court calibration**

**ผลที่ตามมา**: 9 field ในบล็อก BL ยังส่งค่าไม่ได้เลย —
`landing_position` · `landing_zone` · `landing_call` · `ball_speed_kmh` ·
`trajectory_clearance_cm` · `server_position` · `target_box_correct` ·
`serve_attempt_number` · `is_fault` (พ่วง `serve_fault_rate_pct` ใน Phase 2)

> หมายเหตุ: สเปกของลูกค้าเองออกแบบทางออกไว้แล้ว — `BL1 available: false` เป็น
> gate ปิดทั้งบล็อก และ**ตัวอย่าง JSON ในสเปกก็เป็น `"ball": {"available": false}`**
> เราจึงไม่ผิดสเปก แต่ก็ยังไม่ได้ของที่ลูกค้าอยากได้

**ถ้า mark จุดอ้างอิงสนามให้ จะได้อะไรบ้าง** (โค้ดพร้อมแล้ว ไม่ต้องเขียนใหม่):

| field | ได้ไหม | เพราะ |
|---|---|---|
| `landing_position` / `landing_zone` / `landing_call` | ✅ | ตอนลูกแตะพื้น ลูกอยู่บนระนาบพื้นพอดี |
| `server_position` · `target_box_correct` · `is_fault` | ✅ | เท้าผู้เล่นอยู่บนพื้น + derive ต่อ |
| `ball_speed_kmh` | ❌ | ลูกลอยกลางอากาศ ไม่ได้อยู่บนพื้น |
| `trajectory_clearance_cm` | ❌ | ต้องมีแกนความสูง ซึ่ง homography ไม่มี |

**6 จาก 9 field ปลดล็อกได้** — แต่ตัวที่กั้นจริงไม่ใช่ homography

การหาจุดตกต้องเห็นลูกเป็นรูป V (ลงมา → แตะพื้น → เด้งขึ้น) เพดานบนตามทฤษฎี
(สมมติอัลกอริทึมสมบูรณ์แบบ 100%) คือ **1.1% – 11.4% ของเฟรม** เท่านั้น
→ mark สนามแล้วก็ยังได้จุดตกไม่ถึง 10% ของครั้ง

**ลำดับที่แนะนำ**:
1. **60fps ก่อน** — ลูกเคลื่อนเร็ว เฟรมถี่ขึ้นเท่าตัว = โอกาสเห็นช่วง V เพิ่มมาก
2. แล้วค่อย mark สนาม (ทำครั้งเดียวใช้ได้ตลอดถ้ากล้องไม่ขยับ)
3. ถ้ายังไม่พอ → ต้อง label ลูกเพิ่มเพื่อเทรน ball detector

**ต้องเคาะ**: ยอมรับ `available: false` ไปก่อนในเฟสนี้ไหม

รายละเอียด: [BALL_DETECTION_ISSUE.md](BALL_DETECTION_ISSUE.md)

## 6. 🟡 เกณฑ์รับงาน — เสนอใช้เกณฑ์ที่ลูกค้าเขียนไว้เอง

สเปกหัวข้อ "Keyframe selection" ลูกค้าเขียนเองว่า:

> *"Guideline นี้มีไว้เพื่อช่วยเลือก **ช่วงของ keyframe** เท่านั้น
> **ไม่จำเป็นต้องจับเฟรมได้ตรงเป๊ะ** หากอยู่ในช่วงการเคลื่อนไหวเดียวกัน
> ถือว่าใช้ได้"*

และกำกับ `impact` กับ `follow_through_peak` ว่า **(Low Confidence)** ด้วยตัวเอง

เราจึงวัดสองเกณฑ์คู่กัน:

| | เกณฑ์ "ช่วงเดียวกัน" | ±1 เฟรม |
|---|---|---|
| Mode A (end-to-end) | **0.410** | 0.218 |
| **Mode B (ป้อน impact ให้)** | **0.840 ✅ ผ่าน** | 0.759 |

**keyframe logic ผ่านเกณฑ์ 0.80 แล้ว** ส่วนที่ยังขาดคือ hit detection ล้วน ๆ
ซึ่งเป็นงานฝั่งเรา

> ⚠️ **ตัวเลข Mode A ที่เคยแจ้งไว้ว่า 0.506 นั้นสูงเกินจริง** — เพราะโมเดลตรวจ
> จังหวะตีถูกเทรนจากคลิปชุดเดียวกับที่ใช้วัด จึง "จำ" คลิปได้ส่วนหนึ่ง
> พอวัดใหม่แบบตัดผู้เล่นออกทีละคน (Leave-One-Person-Out) ได้ **0.308**
> ตัวเลขในตารางนี้วัดด้วยวิธีหลัง = ตัวที่บอกได้ว่าใช้กับผู้เล่นคนใหม่แล้วจะเป็นยังไง
> Mode B ไม่กระทบ (ป้อน impact จากเฉลย ไม่ได้ใช้โมเดลตัวนั้น)

**ความคืบหน้าของ hit detection** (วัดแบบ LOPO ทุกตัว):

| | ตอนพบปัญหา | + augmentation | **+ ฟีเจอร์วงสวิง** |
|---|---|---|---|
| recall | 0.547 | 0.605 | **0.767** |
| precision | 0.398 | 0.367 | **0.548** |
| **Mode A acceptance** | 0.308 | 0.352 | **0.410** |

ตัวที่ขยับมากที่สุดคือชุดฟีเจอร์ใหม่ที่อธิบาย **"รูปทรงของวงสวิง"** (มุมกวาด ·
การหมุนลำตัว · รูปทรงเส้นทางข้อมือ) — ของเดิมโมเดลเห็นแค่ "ข้อมือเร็วไหม ณ
เฟรมนั้น" จึงแยกการตีออกจากการเดิน/ปรับท่าไม่ได้
รายละเอียด: [SWING_SHAPE_FEATURES.md](SWING_SHAPE_FEATURES.md)

**ต้องเคาะ**: ยืนยันว่าใช้เกณฑ์ "ช่วงการเคลื่อนไหวเดียวกัน" ตามที่เขียนไว้ในสเปก

รายละเอียด: [BENCHMARK_KEYFRAME.md](BENCHMARK_KEYFRAME.md)

### ขอเพิ่ม: มือถนัดของผู้เล่นแต่ละคน

เราพยายามหาเองจากข้อมูลแล้ว 3 วิธี **ไม่ผ่านสักวิธี**:

| วิธี | ผล |
|---|---|
