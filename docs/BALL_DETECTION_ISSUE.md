## สรุปสั้น

ระบบ**มองไม่เห็นลูกเทนนิสที่ลอยอยู่** ในเกือบทุกเฟรม — เห็นจริงแค่ **4.4% – 22%** ของเฟรมทั้งคลิป
ที่เหลือเป็นค่าที่ Kalman filter **เดาต่อเอง** ซึ่งดูเหมือนมีข้อมูลแต่ไม่ใช่การวัดจริง

ผลโดยตรง: **field ที่เกี่ยวกับลูก (จุดตก / in-out / ความเร็วลูก) ยังเชื่อถือไม่ได้**

## 1. ตัวเลขที่วัดได้

### 1.1 detection ดิบจาก YOLO (ยังไม่กรอง)

| คลิป | เจอลูก (conf 0.15) | เจอหลายลูกพร้อมกัน | ช่องว่างยาวสุด |
|---|---|---|---|
| `IMG_0281(BH)` | 99.9% | **91.7%** (เฉลี่ย 2.17 ลูก/เฟรม สูงสุด 5) | 1 เฟรม |
| `IMG_0300B7-SV1` | 24.8% | 7.0% | **221 เฟรม** |
| `IMG_0283A-VLfh` | 4.6% | 0.1% | 127 เฟรม |

คลิป BH ดูเหมือนดีมาก (99.9%) แต่**เจอทีละ 2-5 ลูก** → นั่นคือลูกที่กระจายอยู่บนพื้นสนามและในรถเข็น

### 1.2 แยก "ลูกที่ลอยจริง" ออกจาก "ลูกที่นอนนิ่ง"

*วิธี: detection ที่อยู่ตำแหน่งเดิม (< 8 px) ในเฟรมข้างเคียง ±20 เกินครึ่ง = วัตถุนิ่ง*

| คลิป | detection ทั้งหมด | เป็นลูกนอนนิ่ง | **เฟรมที่เห็นลูกลอยจริง** |
|---|---|---|---|
| `IMG_0281(BH)` | 6,109 | **87.7%** | **22.0%** |
| `IMG_0300B7-SV1` | 1,251 | 53.4% | **14.3%** |
| `IMG_0283A-VLfh` | 52 | 0% | **4.6%** |
| `IMG_0300A4(VL)` | 74 | 0% | **4.4%** |

**คลิป BH: detection 87.7% เป็นลูกที่นอนอยู่กับที่** — Kalman filter จับผิดตัวได้ง่ายมาก
เพราะเงื่อนไข association คือ "bbox ที่ใกล้ตำแหน่งทำนายที่สุด ภายใน 200 px"
([hit_detection.py:130](../loeuf_cv/hit_detection.py#L130)) ไม่มีเงื่อนไขว่าต้องเคลื่อนที่

### 1.3 โอกาสที่จะวัด "จุดที่ลูกตก" ได้จริง

การหา bounce ต้องเห็นลูกเป็นรูป **V** (ลงมา → แตะพื้น → เด้งขึ้น)
เงื่อนไขขั้นต่ำที่สุด: มี detection ของลูกที่ลอยจริง ≥ 2 จุด ทั้งใน 4 เฟรมก่อน **และ** 4 เฟรมหลัง

| คลิป | เฟรมที่พอจะวัด bounce ได้ |
|---|---|
| `IMG_0281(BH)` | **11.4%** |
| `IMG_0300B7-SV1` | **6.5%** |
| `IMG_0300A4(VL)` | **2.0%** |
| `IMG_0283A-VLfh` | **1.1%** |

**นี่คือเพดานบนตามทฤษฎี** — สมมติว่าอัลกอริทึม bounce สมบูรณ์แบบ 100% ก็ยังทำได้แค่นี้
เพราะไม่มีข้อมูลให้ประมวลผล

### 1.4 หลักฐานว่า trajectory ที่ได้เป็นของเดาไม่ใช่ของจริง

ตัวอย่างจาก `IMG_0300B7-SV1` ช่วงก่อนปะทะ:

```
เฟรม  rel   ball_x   ball_y
 345  -26     1392      629
 347  -24     1392      639     x ไม่ขยับเลย
 349  -22     1392      649     y เพิ่ม 10 ทุก 2 เฟรม เป๊ะ
 351  -20     1392      659     -> ความเร่ง = 0
 371    0      nan      nan  <- IMPACT (ไม่มีข้อมูลลูกเลย)
```

ลูกที่ลอยจริงต้องเป็น**พาราโบลา** (แรงโน้มถ่วง) เส้นตรงความเร็วคงที่ = Kalman coasting

วัดทั้ง 54 การเสิร์ฟ:

| ตัวชี้วัด | วัดได้ | ค่าที่ควรเป็น |
|---|---|---|
| ความเร่งแนวดิ่งกลาง (median &#124;d²y/dt²&#124;) | **0.000 px/frame²** | ~4.4 (ตกอิสระที่ 30 fps) |
| เฟรมก่อนปะทะที่ความเร่ง ≈ 0 | **82.9%** | ควรต่ำ |
| stroke ที่ trajectory เป็นเส้นตรง > 80% | **29/52** | ~0 |
| ลูกเป็น NaN ตรงเฟรมปะทะพอดี | **25.9%** | — |

## 2. สาเหตุ (สองอาการคนละเรื่อง)

### อาการ A — สับสนกับลูกที่ไม่ได้อยู่ในการเล่น
พบในคลิปที่ถ่ายมุมกว้างเห็นพื้นสนาม (`IMG_0281`)
มีลูกเทนนิสกระจายบนพื้นและในรถเข็นซ้อมหลายสิบลูก detector เจอหมด
→ 87.7% ของ detection เป็นลูกนิ่ง → ตัวติดตามล็อกผิดตัวได้

**แก้ได้ค่อนข้างง่าย**: กรอง detection ที่อยู่นิ่งออกก่อนเข้า Kalman (โค้ดที่ใช้วัดในเอกสารนี้ทำได้แล้ว)

### อาการ B — มองไม่เห็นลูกที่ลอยอยู่จริง
พบในคลิปวอลเลย์และเสิร์ฟ (4.4% – 14.3%)
ลูกเทนนิสในภาพมีขนาดประมาณ 10–20 px เคลื่อนที่เร็วจน**เบลอเป็นเส้น** (motion blur)
ที่ 30 fps ลูกความเร็ว 100 กม./ชม. เดินทาง ~90 px ต่อเฟรม
YOLO ตรวจจับจากภาพนิ่งทีละเฟรม → วัตถุเล็ก+เบลอ = สิ่งที่ YOLO ทำได้แย่ที่สุด

**แก้ยากกว่า** ต้องเปลี่ยนวิธี (ดูข้อ 4)

## 4. ทางเลือกในการแก้ (เรียงตามความคุ้ม)

### 4.1 กรองลูกที่นอนนิ่งออก — ทำได้เลย
- **แรง**: ต่ำ (~ครึ่งวัน)
- **ได้**: แก้อาการ A แต่ไม่แก้อาการ B
- **ผล**: คลิปแบบ `IMG_0281` จะเลิกล็อกผิดตัว trajectory จะเป็นของจริงมากขึ้น
- ทำได้แน่นอน ควรทำไม่ว่าจะเลือกทางไหนต่อ

### 4.2 เปลี่ยนไปใช้ตัวตรวจจับลูกเฉพาะทาง (TrackNet ตระกูลเดียวกัน) — แนะนำ
- **แรง**: กลาง (~1-2 สัปดาห์ รวมเทรน)
- **หลักการ**: รับภาพ **3 เฟรมติดกัน** พร้อมกันแล้วทำนายเป็น heatmap
  → ใช้**การเคลื่อนไหว**ช่วยหาลูก ไม่ได้ดูแค่รูปร่างในเฟรมเดียว
  → ออกแบบมาสำหรับวัตถุเล็ก เร็ว เบลอ โดยเฉพาะ ซึ่งคือปัญหาข้อ B ตรง ๆ
- **ความเสี่ยง**: ต้องมีข้อมูล label ตำแหน่งลูก — งาน annotate เพิ่ม
- นี่คือวิธีมาตรฐานของงานวิเคราะห์เทนนิสในอุตสาหกรรม

### 4.3 ถ่ายด้วย frame rate สูงขึ้น (120 / 240 fps) — แก้ที่ต้นเหตุ
- **แรง**: ต่ำฝั่งเรา แต่ต้องเปลี่ยนวิธีเก็บข้อมูลฝั่งลูกค้า
- **ได้**: motion blur ลดลงมาก ลูกเดินทางต่อเฟรมน้อยลง 4-8 เท่า
  และแก้ปัญหาจังหวะปะทะ sub-frame ที่เป็นคอขวดเกณฑ์รับงานไปพร้อมกัน
- มือถือรุ่นใหม่ถ่าย 120 fps ได้หมดแล้ว — **ต้นทุนต่ำที่สุดต่อผลที่ได้**

### 4.4 ยอมรับข้อจำกัด — ตัด field ที่เกี่ยวกับลูกออกจากขอบเขต
- ส่งมอบเฉพาะส่วนที่ใช้โครงกระดูก (นับ stroke / แยกท่า / keyframe / ท่าทาง)
- ระบุชัดในเอกสารส่งมอบว่า field เกี่ยวกับลูกยังไม่พร้อม

1. **ทำ 4.1 ทันที** (ต้นทุนต่ำ ได้แน่ ไม่มีข้อเสีย)
