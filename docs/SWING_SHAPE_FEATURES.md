# ฟีเจอร์รูปทรงวงสวิง — ทำไมถึงเพิ่ม และวัดผลได้เท่าไร

> โค้ด: [`loeuf_cv/swing_shape.py`](../loeuf_cv/swing_shape.py) ·
> ตัววัด: [`scripts/ablate_hit_features.py`](../scripts/ablate_hit_features.py)

## ผลสุดท้าย (benchmark เต็ม 16 คลิป / GT 172 / วัดแบบ LOPO)

| | ก่อน | **หลัง** |
|---|---|---|
| detection recall | 0.605 | **0.767** |
| detection precision | 0.367 | **0.548** |
| **Mode A acceptance** | 0.352 | **0.410** |
| Mode B (ป้อน impact) | 0.840 | 0.840 — ไม่กระทบ ✅ |

ความสอดคล้องที่ยืนยันว่าวัดไม่มั่ว: ablation ทำนายที่ threshold 0.60 ว่าจะได้
recall 76.7% / precision 54.8% — benchmark เต็มออกมา **0.767 / 0.548 ตรงทุกหลัก**
(สองตัวนี้คำนวณคนละ pipeline กัน ตรงกันเองแปลว่าไม่มีตัวไหนคิดผิด)

## ปัญหาที่เจอ

hit detection เดิมตอบคำถามได้แค่ **"ข้อมือเร็วไหม"** ไม่เคยถูกถามว่า
**"มันวาดเป็นวงตีจริงหรือเปล่า"**

ฟีเจอร์ทั้ง 21 ตัวของเดิมเป็นอย่างใดอย่างหนึ่งใน 3 กลุ่มนี้เท่านั้น:

| กลุ่ม | ตัวอย่าง | ข้อมูลที่ใช้ |
|---|---|---|
| ขนาดความเร็ว | `wrist_speed`, `speed_pre/post/std` | เฟรมเดียว + ค่าเฉลี่ยรอบ ๆ |
| ระยะห่างวัตถุ | `ball_dist`, `racket_dist` | เฟรมเดียว |
| ตำแหน่งเทียบตัว | `wrist_y_rel`, `wrist_x_rel` | เฟรมเดียว |

พอแปลง velocity → speed **ทิศทางถูกทิ้งไปทั้งหมด** เหลือ `wrist_dir_change`
ตัวเดียวที่ยังเห็นทิศ แต่มันคร่อมแค่ ±2 เฟรม (~70 ms) ขณะที่วงสวิงจริงกินเวลา
ราว 1 วินาที

ผลคือ **การเดินเร็ว การปรับท่า การเก็บลูก ก็สร้าง local max ของความเร็วข้อมือได้
เหมือนกัน** → precision ตกอยู่ที่ 39.8%

## ฟีเจอร์ที่เพิ่ม (11 ตัว)

| ฟีเจอร์ | จับอะไร |
|---|---|
| `chain_order`, `chain_lag`, `chain_gain` | ลำดับพีค สะโพก→ไหล่→ศอก→ข้อมือ (kinetic chain) |
| `sweep_total`, `sweep_ratio` | มุมที่ข้อมือกวาดรอบไหล่ |
| `path_len_bw`, `straightness`, `radius_cv` | รูปทรงเส้นทางของข้อมือ |
| `pre_reversal_cos` | การถอย (backswing) แล้วสวนกลับ |
| `torso_sweep`, `x_factor_max` | การหมุนลำตัว และผลต่างมุมไหล่-สะโพก |

ทุกตัวหารด้วยความกว้างไหล่ (ไม่ขึ้นกับระยะกล้อง/ขนาดตัว) และหน้าต่างเวลา
สเกลตาม fps — เหตุผลเดียวกับที่ `hit_detection.py` ทำ

## Q1 — ฟีเจอร์ใหม่แยก hit ออกจาก non-hit ได้แค่ไหน

AUC บน candidate 2,535 ตัว (is_hit 7.1%)

```
radius_cv        0.843
sweep_total      0.832
torso_sweep      0.782
path_len_bw      0.767
x_factor_max     0.722
───────────────────────
wrist_speed_bw   0.754   <- ฟีเจอร์เดิมที่แรงที่สุด
```

**ฟีเจอร์ใหม่ 4 ตัวแรงกว่าฟีเจอร์เดิมทุกตัว**

`pre_reversal_cos` ให้ค่า **−0.138 ตอนตีจริง เทียบกับ +0.174 ตอนเป็น candidate
ขยะ** — จับ "ถอยแล้วสวน" ได้ตรงตามที่ออกแบบไว้

## Q2 — ใส่เข้าโมเดลแล้วดีขึ้นจริงไหม

Leave-One-Person-Out ระดับ stroke (7 คน · 16 คลิป · GT 172 ลูก)
วัดหลังผ่าน threshold + NMS จริง ไม่ใช่ระดับแถว

| ชุดฟีเจอร์ | augment | recall | precision | F1 |
|---|---|---|---|---|
| เดิม (production) | ไม่ใช้ | 59.9% | 37.3% | 0.460 |
| เดิม | +3 | 64.0% | 45.8% | 0.534 |
| วงสวิงล้วน (11) | +3 | 71.5% | 60.0% | 0.653 |
| **วงสวิง + speed (18)** | **+3** | **69.8%** | **63.5%** | **0.665** |

เทียบขนาดผล: augmentation ทั้งชุดให้ **+0.074** · ฟีเจอร์วงสวิงให้ **+0.205**

### ทำไม "วงสวิง + speed" ชนะ "ทุกฟีเจอร์รวมกัน"

ชุด `all+swing` (32 ตัว) ได้ 0.661 แพ้ `swing+speed` (18 ตัว) ที่ 0.665 —
ตัวที่ถูกตัดออกคือ `ball_dist` / `racket_dist`

เหตุผล: ในคลิปจริงเห็นลูกลอยแค่ 4.4–22% ของเฟรม
([BALL_DETECTION_ISSUE.md](BALL_DETECTION_ISSUE.md)) ที่เหลือถูกเติมด้วย
`9999` ซึ่งเป็น **ค่าคงที่ที่ไม่ได้แปลว่า "ไม่มีลูก"** RandomForest เอาไป
แตกกิ่งแล้วเรียนสิ่งที่ไม่มีอยู่จริง

### ฟีเจอร์ตัวไหนทำงานจริง — และตัวไหนไม่

ความสำคัญจาก RandomForest ที่เทรนด้วยชุดสุดท้าย:

```
sweep_total        26.3%  ┐
radius_cv          17.6%  ├─ ฟีเจอร์วงสวิง = 56% ของโมเดล
path_len_bw        12.4%  ┘
wrist_y_rel         9.7%
torso_sweep         6.7%
chain_gain          6.7%
wrist_speed_bw      6.0%   <- ฟีเจอร์เดิมที่แรงสุด
...
pre_reversal_cos    0.6%
chain_lag           0.6%
chain_order         0.1%   <- แทบไม่มีผลเลย
```

🔴 **kinetic chain ซึ่งเป็นสมมติฐานที่ผมคิดว่าจะแรงที่สุด กลับแทบไม่มีผล**
(`chain_order` 0.1%) เหตุผลที่เป็นไปได้: การหาลำดับพีคด้วย argmax บนหน้าต่าง
สั้น ๆ ที่มี noise สูง ให้ผลไม่เสถียร — ค่าที่วัดได้จึงเป็นการสุ่มมากกว่าลำดับจริง
ตัวที่ทำงานจริงคือฟีเจอร์เชิงเรขาคณิตล้วน ๆ (มุมกวาด · ความแปรปรวนของระยะ
ไหล่-ข้อมือ · ความยาวเส้นทาง)

เก็บ 3 ตัวนี้ไว้เพราะไม่ได้ทำให้แย่ลงและมีต้นทุนคำนวณเกือบเป็นศูนย์ แต่**ห้าม
อ้างว่ามันคือเหตุผลที่ระบบดีขึ้น**

## Q3 — บั๊กที่เจอระหว่างทาง: candidate ที่หายตั้งแต่ด่านแรก

GT 7 ลูกไม่มี candidate อยู่ใกล้เลย → ML ไม่มีโอกาสได้เห็นด้วยซ้ำ

สมมติฐานแรกคือ `min_wrist_speed_px = 8.0` เป็นพิกเซลดิบ (ไม่หารขนาดตัว) แล้ว
ตัดคนที่ยืนไกลกล้องทิ้ง — **วัดแล้วผิด ไม่มีลูกไหนตกด้วยเหตุนี้เลย**

สาเหตุจริงกลับด้านกับที่คิด:

```
speed ที่เฟรมปะทะ (px)    ลูกที่จับได้: median 49    ลูกที่หลุด: median 108
```

**ลูกที่หลุดคือลูกที่ตีแรงที่สุด** เพราะตอนตีแรง จังหวะ follow-through เร็วกว่า
จังหวะปะทะ แล้ว de-dup ของ `_find_wrist_peaks` ยุบ peak ที่ห่างกัน < `window*2`
= 16 เฟรม โดยเลือก **ตัวที่ speed สูงกว่า** → เฟรมปะทะถูกเขี่ยทิ้งทุกครั้ง

การเลือกด้วย speed ดิบตรงนี้เป็นการตัดสินใจที่เร็วเกินไป ปลายทางมี NMS ที่
เลือกด้วย `ml_prob` ซึ่งรู้จักรูปทรงวงสวิงและมีข้อมูลมากกว่ามาก

แก้เป็น `PEAK_MERGE_WINDOW = 8`:

| merge window | เพดาน recall ระดับ candidate | จำนวน candidate |
|---|---|---|
| 16 (เดิม) | 95.3% | 2,250 |
| **8** | **99.4%** | 2,909 (+29%) |

ลดต่ำกว่า 8 ไม่ได้เพดานเพิ่มอีก มีแต่ candidate บวม

## บั๊กที่ test จับได้: มุมกวาดสะสม noise

เทสต์ที่ให้ "คนยืนสั่นอยู่กับที่" พบว่าได้ `sweep_total` **สูงกว่าวงสวิงจริง**
(0.835 เทียบ 0.669)

เหตุผล: ข้อมือมี jitter จาก pose estimator ~0.084 ส่วนของความกว้างไหล่
([augment.py](../loeuf_cv/augment.py) วัดจากข้อมูลจริง) ซึ่งที่รัศมีแขนปกติ
คิดเป็นมุม ~0.04 rad/เฟรม **สุ่มทิศ** พอสะสม `|Δมุม|` ทีละเฟรม 23 เฟรมจะได้
เกือบ 1 rad = เทียบเท่ากวาดจริง 57° ทั้งที่ไม่ได้ขยับไปไหน

แก้ด้วยการวัดมุมข้าม stride (`SWEEP_STRIDE = 3` เฟรมที่ 29.97fps) — การกวาดจริง
มีทิศต่อเนื่องจึงรอด ส่วน noise สุ่มทิศหักล้างกันเองภายใน stride
ผลกับเทสต์: การสั่นอยู่กับที่ลดจาก 0.835 → 0.259 ส่วนวงสวิงจริงไม่ขยับ (0.669)

บนข้อมูลจริงเดิมฟีเจอร์นี้ยังทำงานได้ (AUC 0.832) เพราะ candidate ขยะส่วนใหญ่
คือ **การเคลื่อนไหวจริง** ไม่ใช่การสั่นอยู่นิ่ง ๆ — แต่คุณสมบัตินี้จะกัดเรา
เมื่อคลิปเปลี่ยนคุณภาพ/ระยะกล้อง จึงต้องแก้ก่อนส่งมอบ

## ข้อจำกัดที่ยังเหลือ

- **`path_len_bw` / `straightness` นับระยะปลอมตอน track หลุด** — โค้ดตัดเฟรม
  NaN ออกแล้วต่อจุดที่เหลือเข้าหากัน ช่วงที่หลุดจึงกลายเป็นการกระโดดครั้งเดียว
  ไกล ๆ ที่ถูกบวกเข้าความยาวเส้นทาง วิธีแก้คือทิ้งช่วงที่ข้ามเกิน ~1 ความกว้าง
  ไหล่ต่อเฟรม (ข้อมือจริงเร็วสุดราวนั้น — median ที่วัดได้ 0.68)
  **ยังไม่แก้โดยตั้งใจ**: `hit_classifier.pkl` ที่ใช้อยู่เทรนด้วยนิยามปัจจุบัน
  การเปลี่ยนสูตรฟีเจอร์โดยไม่เทรนใหม่คือ train/serve skew ต้องทำครบชุด
  (แก้สูตร → เทรนใหม่ → วัด LOPO → รัน benchmark) ถึงจะเปลี่ยนได้

- **ตีลม (practice swing) แยกไม่ออก** — มีวงสวิงและ kinetic chain ครบทุกอย่าง
  ตัวที่แยกได้มีแค่ลูกบอล ซึ่งเห็นแค่ 4.4–22% ของเฟรม
  (ลูกค้าแจ้งว่าในคลิปจริงโอกาสเกิดน้อย จึงยังไม่ลงแรงแก้)
- **pl009 ถดถอย** — ยังไม่ทราบสาเหตุ
- **7 คนยังน้อยเกินไป** สำหรับสรุปว่าย้ายข้ามคนได้จริง ต้องรอชุดข้อมูลใหม่
