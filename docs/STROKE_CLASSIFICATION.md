> **สถานะ**: แก้บั๊กใหญ่ 3 ตัวแล้ว · ยังเหลือข้อจำกัดที่แก้ด้วยโค้ดไม่ได้
> **วันที่**: 2026-08-01 · 172 stroke · 16 คลิป · 7 ผู้เล่น

## สรุปตัวเลข

| | ก่อนแก้ | หลังแก้ (in-sample) | หลังแก้ (LOPO) |
|---|---|---|---|
| **รวม** | **0.547** | **0.971** | **0.709** |
| FH | 1.000 | 1.000 | 0.714 |
| **BH** | **0.115** | 1.000 | 0.808 |
| SV | 0.812 | 0.922 | 0.812 |
| **VL** | **0.325** | 1.000 | 0.850 |
| SL | 0.238 | 1.000 | **0.000** |

**LOPO (Leave-One-Person-Out) คือตัวเลขที่ควรใช้คาดการณ์ผู้เล่นใหม่**
ส่วน in-sample คือกรณีที่โมเดลเคยเห็นผู้เล่นคนนั้นตอนเทรน

> ⚠️ ตัวเลข **0.727** ที่เคยรายงานในเอกสารก่อนหน้า **ไม่ใช่ของ production**
> — มาจากการประเมิน classifier แยกต่างหาก ค่าจริงของ pipeline คือ **0.547**

## บั๊กที่แก้ไป 3 ตัว

### 1. ด่าน visibility ปัดทุกอย่างเป็น "FH" (ร้ายแรงที่สุด)

```python
if vis[NOSE] < 0.3 or vis[R_SHOULDER] < 0.3 or vis[L_SHOULDER] < 0.3:
    return "FH"          # <- ไม่ได้ถาม classifier เลย
if vis[wrist_idx] < 0.3:
    return "FH"
```

ตอนตีแบ็คแฮนด์ ผู้เล่นหมุนตัวจนข้อมือข้างถนัดไปอยู่หลังลำตัว MediaPipe จึงให้
visibility ต่ำ **เป็นเรื่องปกติของท่านั้น** ผลคือ:

| ท่า | ถูกปัดเป็น FH ทันที |
|---|---|
| **BH** | **23/26 (88%)** |
| VL | 9/40 (22%) |
| SV | 10/64 (16%) |
| **รวม** | **42/172 (24.4%)** |

trace ยืนยัน — โมเดลตอบถูกแต่ไม่มีใครฟัง:
```
GT=BH  rule=BH  ML=BH(0.96)  final=FH
```

**แก้**: `_nearest_visible_frame()` หาเฟรมใกล้เคียง (±5) ที่มองเห็นพอ
ประเภทท่าไม่เปลี่ยนใน 5 เฟรม ถ้าไม่เจอก็เดินต่อด้วยเฟรมเดิม ดีกว่าเดา FH

### 2. train/serve skew รอบแรก — คนละฟังก์ชันคำนวณ feature

ตอนเทรนใช้ `get_body_metrics()` ตอนใช้งานป้อนค่าจาก `MetricsEngine`

| feature | ตอนเทรน | ตอนใช้งาน |
|---|---|---|
| `arm_backswing_depth_deg` | 125.3 | **−12.8** |
| `contact_distance_from_body_cm` | 58.7 | **12.8** |
| `body_hip_rotation_at_impact_deg` | +5.3 | **−13.6** |
| `body_shoulder_rotation_at_impact_deg` | +4.4 | **−7.4** |

**แก้**: `build_stroke_features()` เป็นแหล่งเดียวที่ทั้งสองทางต้องเรียก

### 3. train/serve skew รอบสอง — คนละ keyframe

ตอนเทรนใช้ keyframe จากเฉลย แต่ `builder` เรียก `classify_stroke` **ก่อน**
`refine_keyframes_for_type` โดยใช้ keyframe ที่ระบบทายเอง

**แก้**: [scripts/train_stroke_classifier_from_cache.py](../scripts/train_stroke_classifier_from_cache.py)
เดินผ่าน `extract_keyframes` + `MetricsEngine` เหมือน builder เป๊ะ

## 🔴 ข้อจำกัดที่แก้ด้วยโค้ดไม่ได้ — SL กับ VL

LOPO ให้ **SL recall 0.000** (ไปปนกับ VL หมด) สาเหตุอยู่ที่การเก็บข้อมูล:

**ทุกคลิปในชุดมีท่าเดียวล้วน ๆ** (ถ่ายแบบซ้อมทีละท่า)

| คลิป | ท่าที่มี |
|---|---|
| `IMG_0266-SL` | SL 10 |
| `IMG_0282(SL)` | SL 11 |
| `IMG_0283A-VLfh` | VL 10 |
| `IMG_0283B-VLbh` | VL 10 |
| `IMG_0300B53-VL` | VL 12 |
| `IMG_0300A4(VL)` | VL 8 |

**คลิปที่มีทั้ง SL และ VL อยู่ด้วยกัน: 0**

ผลที่ตามมา: **"คลิปไหน" ทำนาย "ท่าอะไร" ได้ 100%** อะไรก็ตามที่ติดมากับคลิป
(ระยะกล้อง มุมกล้อง แสง) กลายเป็นตัวทำนายที่สมบูรณ์แบบโดยไม่ได้ดูท่าทางเลย

หลักฐาน — ทดสอบว่าฟีเจอร์ไหนแยก SL/VL ได้ (AUC 0.5 = แยกไม่ได้):

| feature | AUC | หมายเหตุ |
|---|---|---|
| `shoulder_width_frame` | **1.000** | ⚠️ เป็นค่าคงที่ต่อคลิป = จำคลิปได้ ไม่ได้ดูท่า |
| `ankle_y` | 1.000 | ⚠️ เหมือนกัน |
| `arm_follow_through_angle_deg` | 0.805 | อาจใช้ได้ |
| `arm_backswing_depth_deg` | 0.250 | อาจใช้ได้ |

แม้จำกัดเฉพาะ `pl011` ซึ่งเป็นคนเดียวที่มีทั้ง SL และ VL ก็ยังแยกไม่ได้
เพราะ SL กับ VL ของเขามาจาก**คนละคลิป**อยู่ดี

**สรุป: ด้วยชุดข้อมูลนี้ เราพิสูจน์ไม่ได้ว่าโมเดลแยก SL/VL ได้จริงหรือแค่จำคลิป**

## 🔬 คอขวดจริงคือ "จำนวนคน" ไม่ใช่ "จำนวนตัวอย่าง"

LOPO วัดข้าม **คน** ดังนั้นหน่วยที่มีความหมายคือจำนวนผู้เล่นต่อท่า ไม่ใช่จำนวน stroke:

| player | FH | BH | SV | VL | SL |
|---|---|---|---|---|---|
| pl003 | | | | | 10 |
| pl004 | | | 10 | | |
| pl005 | 1 | 7 | 11 | 12 | |
| pl006 | **20** | 3 | 11 | | |
| pl008 | | | 11 | | |
| pl009 | | | 9 | 8 | |
| pl011 | | 16 | 12 | 20 | 11 |

| ท่า | จำนวน**คน** | หมายเหตุ |
|---|---|---|
| FH | **2** | 20 จาก 21 ตัวอย่างเป็นของ pl006 คนเดียว |
| SL | **2** | |
| BH | 3 | |
| VL | 3 | |
| SV | 6 | ท่าเดียวที่ LOPO มีความหมายพอ |

พอ LOPO ตัด pl006 ออก **เหลือ FH ให้เทรน 1 ตัวอย่าง** — ค่าที่วัดได้จึงแกว่ง
ตามความบังเอิญ ไม่ใช่ผลของฟีเจอร์หรืออัลกอริทึม

### ❌ ที่ลองแล้วไม่ได้ผล — normalize ด้วยขนาดตัว (2026-08-02)

สมมติฐาน: 6 feature เป็นระยะพิกัดภาพดิบที่โตตามขนาดคน+ระยะกล้อง (ค่าคงที่ต่อ
คลิป) น่าจะเป็นทางให้โมเดล "เดาว่าคลิปไหน" แทนที่จะดูท่า → หารด้วยไม้บรรทัด
ขนาดตัวน่าจะปิดทางนั้น

| แบบ | LOPO |
|---|---|
| ไม่หารเลย (ของปัจจุบัน) | **0.709** |
| หารแกน x ด้วยความกว้างไหล่ | 0.634 |
| หารแกน x และ y (x=ไหล่, y=ลำตัว) | 0.517 |

**แย่ลงทั้งสองแบบ** — และ FH recall เด้ง 0.714 → 0.095 → 0.524 ระหว่างสามแบบ
ซึ่งเป็นลายเซ็นของค่าที่ไม่เสถียร ไม่ใช่ผลของฟีเจอร์ revert แล้ว
(บันทึกไว้ที่ `schema_builder/classifier.py::swing_window_features` ด้วย)

### ทำไม data augmentation ก็แก้ไม่ได้ด้วยเหตุผลเดียวกัน

augmentation (scale / noise / mirror) เพิ่ม **ความทนทาน** แต่ไม่เพิ่ม
**ความหลากหลายของสไตล์การตี** — สำเนา 21 SL ที่ scale ต่างกัน ยังเป็น SL ของ
คนเดิม 2 คน LOPO จึงไม่ขยับ

เทียบกับ **hit detection** ที่ augmentation ได้ผลจริง (F1 0.461 → 0.544):
โจทย์ที่นั่นคือ "รูปทรงกราฟความเร็วนี้คือจังหวะปะทะไหม" ซึ่งเป็นกฎฟิสิกส์สากล
การยืดหดเวลา/คูณสเกลความเร็วจึงสร้าง "จังหวะปะทะแบบใหม่ที่ถูกฟิสิกส์" ได้จริง
ดู [loeuf_cv/augment.py](../loeuf_cv/augment.py)

> 🔴 **ห้าม mirror เพื่อแปลง FH เป็น BH** — สะท้อนโฟร์แฮนด์ของคนถนัดขวาได้
> "โฟร์แฮนด์ของคนถนัดซ้าย" ไม่ใช่แบ็คแฮนด์ สองท่านี้ใช้กลไกร่างกายคนละแบบ
> (ข้างถนัด ฝ่ามือนำ vs ข้ามลำตัว หลังมือนำ) ไม่ใช่ภาพสะท้อนกัน
> mirror ได้ แต่ต้อง **คง stroke_type เดิม** สลับแค่ `dominant_side`

## วิธีรับมือที่ทำไปแล้ว — ไม่เดาเมื่อไม่มั่นใจ

schema มี `stroke_recommended_action` (`auto_accept` / `coach_review` / `discard`)
อยู่แล้ว แต่เดิมดูแค่ความมั่นใจของ pose **ไม่ได้ดูความมั่นใจของการแยกท่าเลย**

ตอนนี้ `classify_stroke_with_confidence()` คืนความมั่นใจออกมาด้วย และถ้าต่ำกว่า
`stroke_type_review_threshold` (0.60) จะถูกส่งเข้าคิวให้โค้ชตรวจ

ผลบนชุดข้อมูลจริง:

| คิว | จำนวน | ทายท่าถูก |
|---|---|---|
| `auto_accept` | 44 | **100.0%** |
| `coach_review` | 128 | 96.1% |

**ไม่มี stroke ที่ป้ายผิดหลุดเข้า `auto_accept` เลย** — แอปจะไม่แสดงชื่อท่าผิด
ให้ผู้ใช้เห็นโดยไม่มีคนตรวจ

1. **คลิปที่มีหลายท่าปนกัน** (ตีโต้จริง ไม่ใช่ซ้อมทีละท่า) — สำคัญที่สุด

3. โดยเฉพาะ **สไลซ์กับวอลเลย์ในคลิปเดียวกัน**
