# ตัวปรับที่หนึ่ง: regressor จากฟีเจอร์ภาพ

## ที่มา: แยกดูว่า 41% หายไปตรงไหน

Mode A acceptance ได้ 0.410 จาก 344 keyframe (172 stroke × 2) แยกส่วนที่หายได้:

| หายตรงไหน | เสียไป |
|---|---|
| หาลูกไม่เจอเลย (40 จาก 172) | **23.3%** |
| **เจอลูกแล้ว แต่เฟรมปะทะเพี้ยน** | **23.5%** |
| เพดานของ keyframe logic เอง | 12.2% |

**สองก้อนแรกใหญ่เท่ากัน** แต่งานที่ทำมาทั้งหมด (ฟีเจอร์วงสวิง, augmentation,
การแก้ด่านสร้าง candidate) แก้แค่ก้อนแรก

ตัวเลขที่ยืนยัน: ลูกที่ **เจอแล้ว** ได้ keyframe ถูกแค่ 53.4% ทั้งที่เพดาน
(Mode B ที่ป้อนเฉลย) คือ 84.0%

### ทำไมความคลาดนิดเดียวถึงพัง

```
หน้าต่างที่ยอมรับได้ของ impact   median +-4.25 เฟรม
ความคลาดของเฟรมปะทะ p90          7 เฟรม          <- เกินหน้าต่าง
```

และ `backswing_peak = impact - ค่าคงที่` ([keyframes.py](../loeuf_cv/schema_builder/keyframes.py))
→ **เฟรมปะทะเพี้ยน N เฟรม backswing เพี้ยนตาม N เฟรม ทั้งคู่ตกพร้อมกัน**
เป็นความผิดพลาดที่คูณสอง ไม่ใช่บวก

## รากปัญหา: classifier ตอบผิดข้อ

`hit_classifier` ถูกเทรนด้วย label `|frame - เฉลย| <= 5 เฟรม` = **"หน้าต่างนี้
เหมือนการตีแค่ไหน"** ซึ่ง**ไม่ใช่**คำถาม **"เฟรมนี้คือจังหวะปะทะพอดีไหม"**

พอ NMS เลือกด้วย `ml_prob` เฟรม follow-through ที่ความเร็วสูงกว่าจึงชนะเป็นระบบ

วัดจากของจริง (LOPO · 132 stroke ที่ตรวจเจอ):

| | ภายใน 4 เฟรม |
|---|---|
| เฟรมที่เลือกไปจริง | 71.2% |
| ตัวที่ตรงเฉลยที่สุด **ในบรรดา candidate ที่มีอยู่แล้ว** | **88.6%** |

```
37 เคสที่เลือกผิด → ตัวที่ควรเลือกมี ml_prob ต่ำกว่า 100% ของเคส (median -0.099)
30 ใน 37 ผ่านเกณฑ์แล้ว แต่แพ้ NMS ให้เฟรมข้าง ๆ ที่ prob สูงกว่า
```

เป็นรากเดียวกับบั๊ก `PEAK_MERGE_WINDOW` — ตอนนั้นแก้ให้ *เก็บ* ทั้งสอง peak
แต่ยังไม่ได้แก้ว่าจะ *รายงาน* อันไหน

## วิธีแก้: regressor ตัวที่สองที่ตอบถูกข้อ

ทำนาย "ต้องเลื่อนไปกี่เฟรมถึงจะตรงเฉลย" จากฟีเจอร์ชุดเดียวกับที่ classifier ใช้
แล้วปรับเฟรมหลัง NMS — เลื่อนไปเฟรมที่ไม่ได้เป็น candidate ก็ได้ จึงไม่ติดเพดาน
88.6%

จำกัดการเลื่อนไว้ที่ `MAX_SHIFT = 8` เฟรม (ครอบ p90 ของความคลาดพอดี) กันโมเดล
ที่มั่นใจผิดลากเฟรมไปไกลจนแย่กว่าเดิม

## 🔴 ต้องเทรนบนประชากรที่ถูก ไม่งั้นเลื่อนผิดทาง

รอบแรกเทรนบน "candidate ทุกตัวในรัศมี ±10 ของเฉลย" ซึ่งผิด — สองประชากรนี้
เอนเอียงคนละทิศ:

| ประชากร | ค่ากลางของ (เฉลย − เฟรม) |
|---|---|
| candidate ทุกตัวในรัศมี ±10 | **+1** (มาเร็วไป) |
| **เฟรมที่ NMS เลือกจริง** | **−0.5** (ช้าไป) |

**เครื่องหมายกลับกัน** → โมเดลที่เทรนแบบแรกจะเลื่อนผิดทางตอนใช้จริง เป็น
train/serve skew ชนิดเดียวกับที่โปรเจกต์นี้โดนมาแล้ว 3 รอบ

แก้ด้วยการจำลอง threshold + NMS ด้วย **out-of-fold probability** ก่อน แล้วเทรน
เฉพาะเฟรมที่ระบบจะเลือกจริง (`selected_rows()`)

## ผลที่วัดได้

ระดับเฟรม (LOPO · 120 เฟรมที่ระบบเลือกและจับคู่กับเฉลยได้):

| | ภายใน 4 เฟรม | ภายใน 2 เฟรม |
|---|---|---|
| ไม่ทำอะไร | 72.5% | 50.8% |
| เลื่อน −1 ทุกเฟรม (ค่าคงที่ LOPO) | 75.0% | — |
| **refiner (18 ฟีเจอร์)** | **78.3%** | **58.3%** |
| เพดานถ้าเลือกถูกทุกครั้ง | 88.6% | — |

ระดับ benchmark เต็ม (16 คลิป · GT 172 · LOPO ทั้ง classifier และ refiner):

| | ก่อน | หลัง |
|---|---|---|
| **Mode A acceptance** | 0.410 | **0.442** |
| Mode A ±1 เฟรม | 0.218 | **0.253** |
| matched-only ±1 เฟรม | 0.284 | **0.332** |
| detection recall | 0.767 | 0.762 |

ขนาดผลตรงกับที่ทำนายจากตัวเลขระดับเฟรม (+5.8 จุด → ~+3 จุดบน acceptance)
ความสอดคล้องนี้เป็นหลักฐานว่าไม่ใช่ความบังเอิญ

## บั๊กที่เจอในเครื่องมือวัดของตัวเอง

`evaluate()` คืน `before` ที่ผ่าน `abs()` มาแล้ว แต่ลูปตัวเทียบเอาไปคำนวณ
`| |offset| − k |` ซึ่งวัด "ขนาดความคลาดใกล้ k แค่ไหน" ไม่ใช่ "เลื่อนไป k แล้ว
ตรงขึ้นไหม" พอ `|offset|` ส่วนใหญ่ราว 3 ค่าคงที่ +3 จึงดูเหมือนได้ **91.7%**
ทั้งที่ค่าจริงคือ 64.2%

สิ่งที่ทำให้จับได้คือ **ความไม่สอดคล้องของทิศทาง** — ตัววินิจฉัยบอกว่าเฟรมมา
ช้าไป (ควรเลื่อนถอยหลัง) แต่ตัวเทียบบอกให้เลื่อนเดินหน้า สองอย่างนี้เป็นไป
พร้อมกันไม่ได้ ถ้าไม่เอะใจก็คงรายงาน 91.7% ออกไปแล้ว

→ `evaluate()` คืนค่ามีเครื่องหมายเสมอ ผู้เรียกทำ `abs` เอง

## ข้อควรระวัง

- **แต่ละ refiner เทรนจากแค่ 76–114 แถว** น้อยมากสำหรับ RandomForest 18 ฟีเจอร์

- **25% ของแถวแย่ลงหลังปรับ** — เป็นการแลกที่คุ้มโดยรวม แต่ไม่ใช่การปรับปรุงฟรี
- **ต้องเทรนใหม่ทุกครั้งที่ hit classifier เปลี่ยน** เพราะประชากรที่ใช้เทรนคือ
  ผลผลิตของ classifier ตัวนั้น — `retrain_with_new_data.py` ทำให้อัตโนมัติแล้ว
- ตอนรัน benchmark ต้องใช้ refiner ชุด LOPO (`--impact-refiner-dir`) ไม่ระบุ =
  **ปิดการปรับ** ไม่ใช่ใช้ตัวที่รากโปรเจกต์ (ไม่งั้นปนเปื้อนเงียบ ๆ)

# ตัวปรับที่สอง: เสียงกระทบลูก

> โค้ด: [`loeuf_cv/audio_onset.py`](../loeuf_cv/audio_onset.py) ·
> ตัววัด: [`scripts/eval_audio_onset.py`](../scripts/eval_audio_onset.py)

การตีลูกทำให้เกิดเสียง "แป๊ะ" ที่คมกว่าอะไรก็ตามในคลิป และคลิปทุกอันมีแทร็กเสียง
AAC 44.1 kHz ติดมาอยู่แล้ว — ข้อมูลนี้มีมาตลอดแต่ไม่เคยถูกใช้เลย

**เสียงมี resolution สูงกว่าภาพ ~1,470 เท่า** (44,100 ตัวอย่าง/วินาที เทียบกับ
29.97 เฟรม/วินาที) จึงชี้จังหวะปะทะได้ละเอียดกว่าภาพโดยธรรมชาติ

## ⚠️ เสียงบอกไม่ได้ว่า "ใคร" ตี

เสียงตีของอีกฝั่งสนามก็ดังเหมือนกัน จึงใช้เสียงหาการตีเองไม่ได้ —
**ต้องให้ภาพจำกัดหน้าต่างมาก่อนเสมอ** (±6 เฟรม รอบเฟรมที่ระบบเลือกไว้แล้ว)
เสียงทำหน้าที่เดียวคือ "ในหน้าต่างนี้ จังหวะไหนคือปะทะจริง"

## 🔴 เสียงเดินทางช้ากว่าภาพ — และแก้โดยไม่ใช้เฉลย

เสียงวิ่ง 343 m/s กล้องอยู่ห่าง 10-30 m → เสียงมาถึงช้ากว่า 30-90 ms = **1-3 เฟรม**
ถ้าไม่หักออก การปรับด้วยเสียงจะดันเฟรมให้ช้าเป็นระบบ

หักออกโดย**ไม่แตะเฉลย**: ค่าชดเชยของคลิป = ค่ากลางของ (เฟรมที่เสียงเลือก −
เฟรมที่ภาพทำนาย) ทุกลูกในคลิปนั้น ใช้ได้เพราะความคลาดของภาพไม่มีทิศทางชัด
(median +0.5 เฟรม) ส่วนความช้าของเสียงเป็นค่าคงที่ทิศเดียว

หลักฐานว่าเป็นฟิสิกส์จริง ไม่ใช่ artifact: ค่าที่วัดได้อยู่ระหว่าง **+0 ถึง +3
เฟรม และเป็นบวกทั้ง 16 คลิป** — ถ้าเป็นเรื่องบังเอิญมีโอกาส 1 ใน 65,536

## ข้อควรระวัง

- **ต้องมี `ffmpeg` ใน PATH** ไม่มี = ข้ามการปรับเงียบ ๆ (คืนของเดิม ไม่ throw)
- **ต้องมีอย่างน้อย 3 ลูกต่อคลิป** (`MIN_EVENTS_FOR_OFFSET`) ค่ากลางจาก 1-2 ตัว
  ไม่มีความหมาย ถ้าประมาณผิดจะเลื่อนทั้งคลิปผิดตาม
- **ยังไม่ได้ทดสอบกับคลิปที่มีคนตีสองฝั่งพร้อมกัน** — เสียงของอีกฝั่งอาจถูกเลือก
  ถ้ามันดังกว่าและตกในหน้าต่าง ±6 เฟรมเดียวกัน
- แทร็กเสียงมักยาวกว่าวิดีโอเล็กน้อย → ต้องจำกัดเฟรมปลายทางให้อยู่ในคลิป

## บั๊กสองตัวที่เจอตอนต่อของจริง

**1. `.resolve()` หลังย้าย CWD** — `session.video_path` เป็น relative path และ
harness ย้าย CWD ไป temp ก่อน ทำให้ resolve ได้ `<temp>/dataset/...` ที่ไม่มีจริง
→ การปรับด้วยเสียงถูกข้ามทั้งชุด **benchmark ออกมาเหมือนเดิมเป๊ะทุกหลักโดยไม่มี
error สักบรรทัด** แก้ทั้งต้นเหตุและความเงียบ (ตอนนี้พิมพ์คำเตือน)

**2. `video_meta["total_frames"]` ไม่เท่าจำนวนเฟรมที่ track ได้จริง** —
metadata บอก 2414 แต่ decode + track ได้ 2408 · builder เอาเลขจาก metadata ไป
จำกัด keyframe แล้ว index อาร์เรย์ที่สั้นกว่า → `IndexError` พังทั้ง stroke
วัดแล้วพบว่า **8 จาก 16 คลิปไม่ตรงกัน ต่างกันสูงสุด 30 เฟรม** เป็นบั๊ก
production ที่มีมาก่อน เสียงแค่ไปดัน keyframe ให้ตกช่วงนั้นพอดีจนโผล่ออกมา

## บั๊กในตัว harness เอง: คลิปที่พังถูกให้คะแนนด้วยไฟล์เก่า

stage `predict` กับ `score` เป็นคนละคำสั่ง เมื่อ predict พังกลางคัน ไฟล์ผลของ
**รอบก่อน** ยังค้างอยู่ แล้ว score อ่านมาให้คะแนนโดยไม่รู้ว่ามาจากรอบไหน

รอบที่ยังพัง 1 คลิปรายงาน **0.485** พอแก้จนคลิปนั้นรันผ่านจริงได้ **0.471** —
